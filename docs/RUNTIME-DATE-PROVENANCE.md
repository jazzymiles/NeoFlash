# Rust Date calendar and DateTimeFormatter profile

This batch moves **37 existing method paths and 17 existing AS3 property paths** into the common Rust calendar. Shared AS2/AS3 names count once; AS2 `getYear`/`setYear` are separate names. One existing numeric Date constructor is counted separately. `getTimezoneOffset` and `timezoneOffset` remain browser timezone facilities and are deliberately excluded from migration totals.

The adjacent AS3 `flash.globalization.DateTimeFormatter` adds **11 methods and 3 read-only properties**, plus one constructor. Its three constant classes expose ten constants, counted separately: DateTimeStyle (5), DateTimeNameStyle (3), DateTimeNameContext (2). These are useful partial contracts, not complete Flash globalization compatibility. The exact declaration IDs and separate source/execution evidence are in the ignored hour inventory.

## Adapted sources

- Civil-day conversion adapts Howard Hinnant's `year_month_day::to_days` / `from_days` at [date v3.0.4, commit f94b8f36c6180be0021876c4a397a054fe50c6f2](https://github.com/HowardHinnant/date/blob/f94b8f36c6180be0021876c4a397a054fe50c6f2/include/date/date.h). We translated and adapted only the arithmetic into Rust, using Euclidean division, i128 accumulation and the ActionScript millisecond representation. The complete upstream MIT notice is in `THIRD_PARTY_NOTICES.txt`; no C++ library is included. The [author's algorithm explanation](https://howardhinnant.github.io/date_algorithms.html) explains the Gregorian era decomposition.
- The optional-component adjustment approach and AVM1 legacy-year distinction were reviewed against Ruffle's MIT [AVM2 Date](https://github.com/ruffle-rs/ruffle/blob/89a7049965f3090e706265670df309a5128233ac/core/src/avm2/globals/date.rs) and [AVM1 Date](https://github.com/ruffle-rs/ruffle/blob/89a7049965f3090e706265670df309a5128233ac/core/src/avm1/globals/date.rs). We did not bring in Ruffle's VM, chrono integration, parser, GC or timezone engine. Its existing MIT notice accompanies the export.
- Public contracts: [Date](https://airsdk.dev/reference/actionscript/3.0/Date.html), [DateTimeFormatter](https://airsdk.dev/reference/actionscript/3.0/flash/globalization/DateTimeFormatter.html), [DateTimeStyle](https://airsdk.dev/reference/actionscript/3.0/flash/globalization/DateTimeStyle.html), [DateTimeNameStyle](https://airsdk.dev/reference/actionscript/3.0/flash/globalization/DateTimeNameStyle.html), and [DateTimeNameContext](https://airsdk.dev/reference/actionscript/3.0/flash/globalization/DateTimeNameContext.html). Formatter pattern/state code is authored for NeoFlash around the shared calendar and these contracts.

Downloaded references stay under ignored `target/verification/as-runtime-hour-2/date/`. No new Rust dependency is required.

## Shared implementation and boundaries

`as_date.rs` owns Gregorian arithmetic, normalization, clipping, UTC/local component extraction and changes, UTC text formatting, pattern compilation and rendering, formatter style state and operation status. The native host Date stores the timestamp and retains its identity for the existing AMF/JSON/type adapters. The browser provides current time, timezone offset and resolution of already-normalized local civil fields through its timezone database. It also retains the previous parser, locale/string facilities and modern DST policy. No duplicate JavaScript calendar fallback remains for migrated operations.

Numeric dates use the ±8.64e15-millisecond TimeClip range. Each supplied component must be finite and no larger in absolute value than the largest exactly representable integer; outside-profile values produce Invalid Date. Historical SWF coercion differences, host custom conversion objects, ancient timezone offsets containing seconds, Flash-specific date parsing and native subclasses remain outside this profile. The retained modern parser/locale formatting does not become a Rust migration merely because the numerical calendar changed.

DateTimeFormatter receives locale names and style templates through browser Intl, then Rust validates and interprets the templates and builds the final text. Its initial calendar is Gregorian with Latin digits; custom patterns support `y M L d E H h K k m s S a z Z`, quoted literals and doubled apostrophes. Unsupported pattern letters/widths and unterminated quotes diagnose atomically without replacing the previous pattern. Patterns are limited to 4,096 characters, locale profiles to 128 KiB and output to 65,536 bytes. Native subclasses and non-Gregorian calendars are unsupported. Month format/standalone contexts are distinguished; weekday names currently share the host standalone forms for both contexts. Historical platform-specific patterns and complete era/week-field behavior are not claimed.

Names and locale enumeration return the project's actual `Vector.<String>` values. `getAvailableLocaleIDNames` advertises a bounded list of thirty common candidate locales filtered by host support; it is not exhaustive enumeration of every browser locale. Requests use host locale negotiation, and the actual locale is reported. Locale counts are not additional API entries. The browser must provide Intl.Locale week information. Unsupported browser facilities produce an actionable error.
